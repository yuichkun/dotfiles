# フェーズ別の会話と成果物の例

各フェーズに着手する前に、この文書の該当節を読んで「会話の粒度・止まり方・成果物の形」を合わせる。

## この文書の使い方（最初に必ず読む）

- **登場する人物・数字・提案内容はすべて架空**（Aさん・Bさんという2人の架空エンジニアを使う）。実在の誰かではないし、過去の制作事例でもない
- **内容を流用してはいけない**。ここから写してよいのは「形式・粒度・トーン・手順」だけ。提案の中身（表現形式・物語の切り口・コピー）は毎回、実在の対象者の調査結果から発想し直す。例に出てくる「点検記録簿」「路線図」等をそのまま候補に出したら、それは発想の放棄であり誘導になる
- 例は2人分ある理由: 素材の厚さで進め方がどう変わるかを示すため
  - **Aさん**（架空）: バックエンド8年目。GitHub 47リポジトリ、技術記事18本（障害対応の振り返り連載が人気）、登壇2回、個人サイトなし
  - **Bさん**(架空): フロントエンド3年目。リポジトリ9、記事3本、登壇0。素材薄め
- 例の多くは会話の吹き出しで書いてあるが、提示の基本媒体は進行ハブ（`references/progress-hub.md`）。ハブが使える環境では、ここにある内容と粒度をハブ画面に載せ、TUIには短い通知だけ出す。会話文のまま使うのはブラウザを開けない環境のフォールバック時

目次: Phase 0 診断 / Phase 1 調査 / Phase 2 方向性提案 / Phase 3 決定書 / Phase 4 素材台帳 / Phase 5 初稿確認 / Phase 6 検証報告 / Phase 7 フィードバック

---

## Phase 0: 厚み診断の提示例

診断は表+短い所見で出す。数字だけ並べて終わらない（所見が次の提案の根拠になる）。

> **素材の厚み診断（Aさんの例・架空）**
>
> | 項目 | 件数 | 備考 |
> |---|---|---|
> | 職歴 | 3件 | うち2件に詳細説明あり |
> | リポジトリ | 47 | スター上位: 運用ツール2件（★120/★45） |
> | 技術記事 | 18本 | 障害対応の振り返り連載（6本）に反響集中 |
> | 登壇 | 2回 | 社内勉強会1・カンファレンスLT1 |
> | 画像素材の見込み | 薄い | 個人サイトなし。記事のOGPとスライド表紙が主 |
>
> 所見: 文章素材（連載）が最も厚く、ビジュアル素材は薄い。文章の引用を主役にできる表現が向きそう。
> このまま調査に進んでいい？ 次に母集団の全件リストと、読みの深さの選択肢を概算つきで見せる。

Bさん（素材薄）の場合の所見の書き方: 「全体に素材は薄めだが、リポジトリREADMEの書き込みが丁寧で、9件全部を深掘りしても規模は小さい。薄いなりに密度の高い小品（1〜3画面）を狙うのがよさそう」— **素材が薄くても中止せず、規模の設計に翻訳する**。

## Phase 1: 調査の例

### 全件読解前のGO確認（読みの深さは本人が選ぶ）

> 母集団を確定した。重複とforkを除いて全64件（職歴3・リポジトリ41・記事18・登壇2。一覧を添付）。全件の実コンテンツを開いて読む。深さは選べる:
> - ライト: 冒頭+見出しだけ（概算◯◯トークン）
> - 標準: 種別ごとの要所 — README全文・記事は導入+見出し+結び（概算◯◯）
> - フル: 全文（概算◯◯）
> どれで回す？

### coverage report の提示例

ハブの coverage 画面に載せる内容（フォールバック時は同じ構成を会話で）:

> 全64件の読解が終わった。読めたのが59件、読めなかったのが3件（旧個人サイトなど — アーカイブまで試してダメだった）、重複が2件。
> 分かった骨子: 障害対応の連載が反響・内容ともに突出していて、リポジトリ群も「予防を仕組みにする」方向で一貫している。
> 次は重要度（S/A/B/C）を付けて見せる。進めていい？

「成果物はこちらです: research/coverage-report.md, integration.md, …」のような内部ファイルの列挙は報告として不可（どれを読めばいいか本人に判断させる形になる）。

### 採点結果の提示

採点ボード（S/A全件を画像付きで比較できるハブ画面。仕様は `references/progress-hub.md`）を開いて見せ、「上下させたいものがあれば言って。特にS級（作品の柱）は納得いくまで直す」と本人に調整権を渡す。S級だけ列挙して「Aから上げたいものは？」と聞かない — 比較対象が見えていない状態では判断できない。

## Phase 2: 方向性提案の例（チェックポイント①）

提示の形: **軸（系統）× 案** の一覧を先に見せ、各案は静的HTML1枚の雰囲気見本で確認できるようにする。

> 調査から見えたAさんの軸は「障害を消す人 — 事後対応から予防設計へ」だと読んだ。この軸を活かせる表現の方向を、3系統×2〜3案で用意した（見本は全部1画面の使い捨て。気に入らない系統は丸ごと捨てて大丈夫）:
>
> - 印刷物系: ①設備の点検記録簿風 ②官報・公示風
> - 地図・図面系: ③システム構成図が年々変わっていく図面集 ④インシデントの「ヒヤリハット地図」
> - 計器・記録系: ⑤監視ダッシュボードの10年分リプレイ
>
> それぞれの見本を並べたボードを作った。どれが「自分っぽい」か、逆にどれが気持ち悪いかを教えてほしい。

会話の要点:
- 案を1つに絞って持って行かない。**選ぶのは本人**
- 「どれがいい？」だけでなく「どれが気持ち悪いか」も聞く（落選理由が後の判断材料になる）
- 見本は捨てられる粒度（1案=1画面、作り込まない）
- ※上の「点検記録簿」等はAさん（架空）から発想した例。実在の対象者には、その人の調査結果から軸ごと発想し直すこと

### 雰囲気見本1案の骨格（コードレベルの粒度）

1案 = 1つのHTMLファイル。以下の骨格の**構造だけ**を踏襲する（`★`の中身は毎回、対象者の調査結果から決める。lorem ipsum等のダミーテキストと、**創作した年号・数字**は使用禁止 — 見本の説得力は実素材から出るし、見本段階の創作は捏造の入口になる）:

```html
<!DOCTYPE html>
<html lang="ja">
<head>
<meta charset="utf-8">
<title>案3 ★案の名前（軸: ★系統名）</title>
<style>
  /* 支配色1 + アクセント1 + ニュートラル。★色は対象者の素材や題材から引く */
  :root { --bg: ★; --ink: ★; --accent: ★; }
  body { margin: 0; background: var(--bg); color: var(--ink);
         font-family: ★書体を1つ決める（明朝systemスタック等）; }
  /* 質感（紙・グレイン・罫線など）を1つだけ入れる。全部盛りにしない */
</style>
</head>
<body>
  <!-- ①タイトルの組み方: 書体・スケール感が伝わる大きな文字組み -->
  <header>★この表現でのタイトルの見せ方（対象者の名前 or 作品タイトル案）</header>
  <!-- ②実素材を1点だけ: 調査書にある本物の一文・数字・実績を置く -->
  <section>★例: 本人の記事の一文の引用 + 出典表記</section>
  <!-- ③案の自己紹介: 選抜ボードで見たときに意図が分かるように -->
  <footer>案3 ★案名 — 軸: ★系統 / 意図: ★この表現が何を伝えるかを1行</footer>
</body>
</html>
```

目安: 50〜150行・スクロールなしの1画面・依存ゼロ（CSSはインライン、外部読み込みなし）。

### 選抜ボードの構造

全案を1ページで見比べられるようにする: 各案へのリンク（またはiframe埋め込み）+ 案名 + 軸 + 意図1行、を並べただけの素朴な一覧でよい。ボード自体を装飾しない（判断対象は各案であってボードではない）。

## Phase 3: 決定書の全文例（チェックポイント②）

決定書は1枚。これを本人が承認したら作り込みに入る。

> # 決定書（Aさんの例・架空）
>
> ## 物語の背骨（すべて調査書の事実に基づく）
> - 起点: 2016年、入社2週目に本番障害の対応に入る（連載第1回の記述）
> - 転機: 2021年、振り返り連載開始。「対応する人」から「書き残す人」へ
> - 現在: 2024年、SREチーム立ち上げ。「仕組みで防ぐ人」へ
> ## 形式と規模
> - 「設備点検記録簿」風の1作品・6ページ。文章素材が厚くビジュアルが薄いという診断に合わせ、引用を主役にする
> ## 素材の方針
> - 実素材のみ（記事の引用・リポジトリのREADME・スライド表紙）。AI生成画像は使わない
> ## やらないこと
> - 音声 / 複数作品 / 出典のない脚色
>
> これで作り始めていい？（承認後も初稿の段階でもう一度見せる）

## Phase 4: 素材台帳の例

使う候補の素材はすべて台帳（`assets/ledger.json`）に載せてから使う。**被写体の確定手段を書けない画像は使えない**（use: false のまま残す）。

```json
[
  { "file": "slide-2023.png", "source_url": "（スライド共有サービスのURL）", "subject": "2023年LT登壇のスライド表紙", "subject_evidence": "スライドページのタイトルと本人名の一致", "attribution": "本人作成スライド", "use": true },
  { "file": "ogp-postmortem1.png", "source_url": "（記事URL）", "subject": "連載第1回のOGP画像", "subject_evidence": "記事ページのメタタグから取得", "attribution": "本人記事のOGP", "use": true },
  { "file": "team-photo.jpg", "source_url": "（会社ブログURL）", "subject": "不明（誰の何の集合写真か特定できず）", "subject_evidence": "", "attribution": "", "use": false }
]
```

## Phase 5: 初稿トーン確認の例（チェックポイント③）

成果物の構造は `site/` フォルダ内で完結させる:

```
site/
  index.html      入口（1ページ完結ならこれだけ）
  assets/         使用画像（台帳で○になったものだけ）
  （複数ページ構成なら page2.html 等を並べ、相互リンクは相対パス）
```

全部作ってから見せない。トーンが分かる最小の状態（表紙+1ページなど）で一度止まる。

> 初稿の最初の2ページだけ組んだ。色・書体・引用の見せ方がこの方向でいいか見てほしい。
> 特に確認したいのは: ①見出しの言い回しが「本人の声」として自然か ②引用の量が多すぎないか。
> ここでの指摘は残り4ページ全部に反映するから、遠慮なく。

## Phase 6: 検証報告の例

検証は結果の数字で報告する。「確認しました」だけの報告はしない。

> 検証結果:
> - 参照整合: HTML 6件・ローカル参照41件を全数検査 → 問題0件（check_refs.py 実施）
> - レイアウト: はみ出し0・文字切れ疑い0（headless Chromeで機械測定）
> - 目視: 引用ブロックの最長ページと画像キャプション3箇所を等倍確認 → 問題なし
> - file:// 直開き・ローカルサーバの両方で表示確認済み

## Phase 7: フィードバックの流れの例

1. 「完成した。ブラウザで開くね」— 開くところまで自分でやる。開けない環境でだけ「`site/index.html` をブラウザで開いてみてほしい」とリンクを渡す
2. 鑑賞後: 「フィードバックを7問、一問ずつ聞かせてほしい（実験のため全試行共通の質問）」→ `references/feedback-questions.md` の質問を「質問 1/7」の形式で一問ずつ・一言一句そのまま提示。回答の受け方は同ファイルに従う
3. スクリーンショットを撮って `review/` に保存する。渡すときの文型: 「スクリーンショットは撮影済みで、追加の撮影は要らない。esaコメントには `review/01-top.png` と `review/02-highlight.png` の2枚をそのまま添付して」。自分で撮れない環境では、撮ってほしい箇所を指定して本人に依頼する
4. 回答を `assets/feedback-template.md` の形式でまとめる。メタ情報（診断値・モデル・時間・トークン・チェックポイント記録・出典タグ集計・検証実施状況）は自分で埋める
5. 「まとめたmdがこれ。内容を確認して問題なければ、esa のこのポストに**md本文をコメントとして貼り、`review/` の画像を添付**してほしい: https://lapras.esa.io/posts/16747 」（**代わりに投稿しない**）
6. もし途中で終了する場合: 「どのフェーズで・なぜやめたか、一行だけでも esa にコメントしてもらえると実験として貴重」と案内する
