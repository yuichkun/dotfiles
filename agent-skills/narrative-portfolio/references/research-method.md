# 調査の方式 — 母集団・全件読解・source card・採点

## 原則: 読む前に選抜しない

深掘り対象をメタデータ（タイトル・スター数・いいね・OGP）で選ぶと、次のバイアスで重大ソースを落とす:

- **選抜バイアス**: 選抜の入力が「読む前に手に入る情報」に偏る
- **取得容易性バイアス**: テキストを取りやすい記事・READMEが有利になり、JS依存サイト・動画・画像中心の作品・消失ページが不利になる
- **人気バイアス**: スターやいいねの多いものを重要と誤認し、本人固有だが反応数の少ない作品を落とす

順序は「母集団を定義 → 全件を読む → 統合 → 採点 → 必要なら深掘り」。採点（S/A/B/C）は coverage report を本人に見せた後にだけ行う。

## 素材の厚み診断と母集団の列挙（Phase 0）

LAPRAS MCP のデータから機械的に測り、最初に本人へ提示する。フィードバック集計時に「結果の質が素材の厚みに依存していたか」を判断する母数になるので、必ず数字で残すこと。

測定項目:

- 職歴の件数（詳細説明の有無も）
- アウトプットの件数と内訳（リポジトリ／記事／登壇・イベント／動画）
- 外部に辿れるリンクの種別（GitHub・Zenn・Qiita・note・はてな・YouTube・個人/会社サイト・取材記事など）
- 画像素材の見込み: サムネイル・OGP・サイト内画像が取れそうなソースの数
- スター・いいね等の反響数の分布（上位数件の値）

診断結果が薄くても中止しない。規模を素材に合わせる（例: 大作1本ではなく、密度の高い小品1本）。

あわせて調査の**母集団**を確定する:

- 職歴・アウトプット・Selection・外部リンクを全件列挙する
- **一覧系ツール（get_outputs 等）のページング・件数上限を必ず確認し、最終ページまで辿る**。取得合計件数を LAPRAS プロフィール画面の表示件数と突合し、一致した数字を log.md に記録する。一致しないうちは先へ進まない（1ページ目だけを全集合と思い込むのが典型事故で、以後の coverage 検証は内部整合しか見ないため検出できない）
- 重複・fork・翻訳版・同一案件の複数記事を識別する（この段階で重要度は決めない）
- 境界は「LAPRAS から直接到達できる一次ソース」と「案件を裏づける公式ソース」の一段階まで。無限にリンクを辿らない
- 確定した母集団は `research/population.json` に保存する: 全件の `{"id", "title", "url", "type", "status"}` の配列。初期 status は `"pending"`

## canonical identity（Phase 0）

本人の氏名・組織名・作品名の正式表記など、作品全体の主体を特定する文字列は「推測してよい本文」ではない。最初に一次情報から確定し、以後すべての工程が参照する:

- 本人運営の一次ソース（本人サイト・所属組織の公式サイト・プロフィールの構造化データなど）を最低2件照合し、原文どおりの表記を `research/identity.json` に保存する
- ローマ字・かなからの漢字補完、記憶や変換候補からの再構成は禁止。許されるのは原文からのコピーだけ（LAPRAS MCP に漢字表記が無くても、一次ソースには大抵書いてある。identity 確定に必要な2件だけはこの時点で先行して読んでよい — 全件読解の先取りであり、選抜ではない）
- source card・採点・見本・成果物・生成スクリプトはこのファイルを参照し、氏名をリテラルで書かない

`identity.json` の形式（このキー構成で書く。検査スクリプト check_identity.py がこの構造を前提にする）:

```json
{
  "name": {
    "value": "山田 太郎",
    "source_urls": ["https://…", "https://…"],
    "source_locator": "本人サイトのプロフィール欄 / note の構造化データ"
  },
  "name_variants": ["Taro Yamada", "yamada-taro", "やまだたろう"],
  "organizations": [{ "value": "…", "source_urls": ["…"] }],
  "forbidden": [],
  "ignore": []
}
```

- `name_variants`: 正しいが canonical でない表記（ローマ字・かな・ハンドル名）を全部登録する
- `forbidden`: 調査中・検査中に見つかった**誤表記**。成果物に1件でも現れたら固有名詞検査が失敗する
- `ignore`: 固有名詞検査が「疑わしい」と挙げたが正当だった文脈文字列（検査のノイズ抑制用）

## GO確認と読みの深さ（Phase 1 の入口）

母集団の全件リスト・規模・概算トークンを本人に示してGOをもらう。読みの深さはスキル側で決め打ちにせず、選択肢と概算をセットで見せて**本人が選ぶ**:

- ライト: 冒頭+見出し構造だけ
- 標準: 種別ごとの要所（README=全文または冒頭+見出し／記事=導入+見出し+結び／動画=説明文+字幕冒頭／サイト=トップの本文）
- フル: 全文

## パス1: 全件読解

母集団の100%に `read / inaccessible / duplicate / irrelevant` のいずれかを付ける。

- `read` は実コンテンツ（本文・README・動画字幕・作品画面など）を開いた場合だけ。メタデータだけで読んだ扱いにしない
- `irrelevant` は機械的に判定できるものだけ（fork・dotfiles・翻訳重複など）。「読んだが物語に使わない」は irrelevant ではなく tier C
- 保存単位は**1カード = 1ファイル**（`research/cards/<id>.json`）。一枚岩のJSONへの追記方式は、コンテクスト圧縮後の書き直しで過去カードを失うので禁止
- 10件前後のバッチで回し、カードを書くたび `population.json` の該当 status を更新する。各バッチの終わりに残数（pending 件数）を log.md に記録する。中断・再開は population.json の pending を数えるだけでできる — 記憶で「どこまで読んだか」を再構成しない
- subagent が使えるならソース種別ごとにバッチ分担し、全員が同一フォーマット（下の source card）で返す。使えなければ main agent が逐次バッチで回す
- 取得できないソースはフォールバックを順に試す: ブラウザ → 公式API → 代替掲載先 → Webアーカイブ → 動画字幕。最後まで読めなければ `inaccessible` と記録する（それも事実性の一部）

### source card（統一形式）

1ソース = 1カード。JSON でも md でもよいが、後から機械集計できるよう構造を揃える:

```json
{
  "id": "ソースの識別子",
  "title": "ソースの名前",
  "status": "read | inaccessible | duplicate | irrelevant",
  "accessed": "実際に開いたもの（本文 / README / 字幕 / 作品画面 など。inaccessible なら試したフォールバック）",
  "summary": "何についてのソースか",
  "role": "本人の役割・問題意識・行動・結果",
  "novel": "他のソースにない新情報",
  "visual": "画像・動画・音声素材の有無とざっくりの内容",
  "source_url": "出典URL",
  "unknowns": "不明点"
}
```

`visual` はビジュアル実現性の記録。素材候補（OGP・README内画像・スクリーンショット・動画）の存在と種類、何が写っていそうかの見当まで書く。Phase 2 の方向性提案が「使える素材の量と質」を知った上で発想できるようにするため。原寸取得・品質監査・帰属確定はここではやらない（Phase 4 の仕事）。

card に書く固有名詞（人名・組織名・作品名）は一次ソースの原文からコピーする。補完・言い換え・変換をしない。

## 統合と coverage report

- カード全件を一度に読み込んで統合しない。種別ごと・バッチごとに中間ダイジェスト（`research/digest-<種別>.md`）を作り、ダイジェスト同士を統合する（小コンテクストの環境でも取りこぼさないため）
- 全 source card を統合し、同一案件の複数ソース・転載・翻訳・fork をまとめる
- **同一人物・同一案件の表記揺れを照合する**。canonical identity や card 間で矛盾する表記が見つかったら、一次ソースに戻って確定するまで先へ進まない（ID・件数・schema の検証が通っても、表記の照合をしなければ矛盾は検出できない）
- 時系列・反復テーマ・転機・矛盾・空白期間を抽出する
- coverage report（ステータスの集計と `inaccessible` の一覧・試したフォールバック）を本人に提示する。**これを見せるまで採点を始めない**

## 重要度採点

coverage report の提示後、全ソースに S/A/B/C の tier を付け、根拠つきで本人に提示する。採点の4軸:

- 関与度（本人がどれだけ中心的に関わったか）
- 反響（スター・いいね・取材・受賞などの外部評価）
- 転機性（キャリアの流れを変えた度合い）
- 素材の強さ（画像・引用など、表現に使える素材があるか）

反響は4軸の1つにすぎない。取得しやすさやスター数だけを重要度の根拠にしない。最終調整は本人が行う。S 級（目安10件前後）が作品の柱になる。

## パス2: 深掘りと調査書

採点が確定したら、**S級は全件を必須で**、A級は作品の柱に使う可能性があるものを「1対象 = 1調査書」に昇格させる（S級の昇格が必須なのは、出典タグ集計が調査書の claims からしか作れないため。省略すると実験の計測データが欠落する）。全文深掘りの対象と規模を再提示してGOをもらってから行う。

調査書は `research/dossiers.json` に配列でまとめる。claim には必ず id を振る:

```json
{
  "id": "対象の識別子",
  "title": "対象の名前",
  "claims": [
    {
      "id": "対象id#連番（例: repo-oncall-helper#1）",
      "text": "事実の記述（1文単位）",
      "source_url": "出典URL",
      "source_tag": "mcp | external-public | local-auth"
    }
  ],
  "tier": "S | A | B | C",
  "tier_reason": "採点の根拠",
  "notes": "取得できなかったソース等の記録"
}
```

## 出典3値タグ（必須）

すべての出典に付ける。この集計が実験の検証軸（LAPRAS MCP 外データへの依存度）の判定材料になり、将来の製品判断（サービス内展開かスキル配布か）に直結する。

| タグ | 意味 |
|---|---|
| `mcp` | LAPRAS MCP から取得したもの（職歴・アウトプット一覧・スコア） |
| `external-public` | 外部の公開情報（README・記事本文・取材記事・公開サイト・画像） |
| `local-auth` | ユーザーローカル/認証つきでしか取れないもの（private リポジトリ、ローカルの資料） |

### 集計の定義と手順

- 集計対象は「**最終作品に実際に使った claim**」= `research/used-claims.json` の全件（重複除去後）。S級限定でも目分量でもない
- `used-claims.json` は Phase 5 で成果物に事実（文・数字・固有名詞）を書くたびに追記する配列: `[{"claim_id": "repo-oncall-helper#1", "used_in": "site/index.html"}]`。実装が終わってから記憶で再構成するのは禁止
- 集計は `scripts/count_source_tags.py <作業ディレクトリ>` を実行し、**出力をそのまま feedback md に転記する**。手集計・目分量は禁止。スクリプトは未解決の claim_id や不正タグを検出したら exit 1 を返す — 0 になるまで直す
